一句话主张。 不必为每种工具堆人类标注，也不必在下游题上写死「本题用计算器」：让语言模型在预训练语料上自己采样 API 调用，只留下能降低后续词损失的那些，再微调——模型就能决定调用哪些 API、何时调用、传什么参数、如何把结果写进下文。

和 AI 工程、智能体 / Cordiverse 的关系

Toolformer 是协议 / 循环谱系里「工具使用」的基石：把计算器、问答、搜索、翻译、日历收成可插入文本的 API。对 AI 工程的用处可以收成一句：工具调用可以当语言建模目标来学，而不必先做智能体框架。

它和 ReAct 不同：这里没有任务级的思考–行动交错示范，过滤标准是下一标记的损失。和 Cordiverse 的关系见读后评论：作者已写明不会链式调用、不会交互改查询；更没有卸载与依赖。此处不占导读。

Abstract

Language models (LMs) exhibit remarkable abilities to solve new tasks from just a few examples or textual instructions, especially at scale. They also, paradoxically, struggle with basic functionality, such as arithmetic or factual lookup, where much simpler and smaller models excel. In this paper, we show that LMs can teach themselves to use external tools via simple APIs and achieve the best of both worlds. We introduce Toolformer, a model trained to decide which APIs to call, when to call them, what arguments to pass, and how to best incorporate the results into future token prediction. This is done in a self-supervised way, requiring nothing more than a handful of demonstrations for each API. We incorporate a range of tools, including a calculator, a Q&A system, a search engine, a translation system, and a calendar. Toolformer achieves substantially improved zero-shot performance across a variety of downstream tasks, often competitive with much larger models, without sacriﬁcing its core language modeling abilities. 摘要

语言模型（LM）表现出仅从少量示例或文本指令就能解决新任务的显著能力，尤其是在规模增大时。它们也悖论式地在算术或事实查找等基本功能上挣扎，而这些正是更简单、更小的模型所擅长的。在本文中，我们表明 LM 可以经由简单 API 自学使用外部工具，并同时获得两方面的优点。我们引入 Toolformer，一个被训练来决定调用哪些 API、何时调用、传递什么参数、以及如何最好地将结果纳入未来标记预测的模型。这以自监督方式完成，每种 API 只需少量示范。我们纳入一系列工具，包括计算器、问答系统、搜索引擎、翻译系统与日历。Toolformer 在多种下游任务上取得显著改善的零样本性能，常常可与大得多的模型竞争，同时不牺牲其核心语言建模能力。

We ﬁrst sample up to k candidate positions for doing API calls by computing, for each i ∈{1, . . . , n}, the probability pi = pM(<API> | P(x), x1:i−1) that M assigns to starting an API call at position i. Executing API Calls As a next step, we execute all API calls generated by M to obtain the corresponding results. How this is done depends entirely on the API itself – for example, it can involve calling another neural network, executing a Python script or using a retrieval system to perform search over a large corpus. Filtering API Calls Let i be the position of the API call ci in the sequence x = x1, . . . , xn, and let ri be the response from the API. Further, given a sequence (wi | i ∈N) of weights, let Li(z) = − n X j=i wj−i · log pM(xj | z, x1:j−1) be the weighted cross entropy loss for M over the tokens xi, . . . , xn if the model is preﬁxed with z. We compare two different instantiations of this loss: L+ i = Li(e(ci, ri)) L− i = min (Li(ε), Li(e(ci, ε))) where ε denotes an empty sequence. The former is the weighted loss over all tokens xi, . . . , xn if the API call and its result are given to M as a preﬁx;3 the latter is the minimum of the losses obtained from (i) doing no API call at all and (ii) doing an API call, but not providing the response. Intuitively, an API call is helpful to M if providing it with both the input and the output of this call makes it easier for the model to predict future tokens, compared to not receiving the API call at all, or receiving only its input. Given a ﬁltering threshold τf, we thus only keep API calls for which L− i −L+ i ≥τf holds, i.e., adding the API call and its result reduces the loss by at least τf, compared to not doing any API call or obtaining no result from it. 执行 API 调用

下一步，我们执行 M 生成的所有 API 调用以获得相应结果。如何做完全取决于 API 本身——例如，它可以涉及调用另一个神经网络、执行一段 Python 脚本，或使用检索系统在大语料上搜索。每个 API 调用 ci 的响应需要是单一文本序列 ri。

过滤 API 调用

令 i 为 API 调用 ci 在序列 x = x1, …, xn 中的位置，令 ri 为来自 API 的响应。进一步，给定权重序列 (wi | i ∈ N)，令

Li(z) = − ∑_{j=i}^{n} w_{j−i} · log pM(xj | z, x1:j−1)

为若模型以 z 为前缀，M 在标记 xi, …, xn 上的加权交叉熵损失。我们比较此损失的两种不同实例化：

L+_i = Li(e(ci, ri))

L−_i = min (Li(ε), Li(e(ci, ε)))

其中 ε 表示空序列。前者是若将 API 调用及其结果作为前缀给 M，在所有标记 xi, …, xn 上的加权损失；后者是（i）完全不做 API 调用与（ii）做 API 调用但不提供响应所得损失的最小值。直观上，一次 API 调用对 M 有帮助，如果同时向它提供此次调用的输入与输出，使它比完全不接收 API 调用、或只接收其输入更容易预测未来标记。给定过滤阈值 τf，我们因而只保留满足

L−_i − L+_i ≥ τf

的 API 调用，即加入 API 调用及其结果使损失至少降低 τf，相比不做任何 API 调用或从中得不到结果。

工具

我们探索一系列工具以应对常规 LM 的不同短板。我们加诸这些工具的唯一约束是：（i）其输入与输出都能表示为文本序列；（ii）我们能获得其预期用途的少量示范。具体而言，我们探索以下五种工具：问答系统、维基百科搜索引擎、计算器、日历与机器翻译系统。与这些工具关联的 API 的一些潜在调用与返回字符串示例见表 1。我们在下面简要讨论所有工具；进一步细节见附录 A。

问答

我们的第一种工具是基于另一个 LM、能够回答简单事实性问题的问答系统。具体而言，我们使用 Atlas（Izacard et al., 2022），一个在 Natural Questions（Kwiatkowski et al., 2019）上微调的检索增强 LM。

计算器

我们的第三种工具是搜索引擎，给定搜索词，返回来自维基百科的短文本片段。与问答工具相比，此搜索使模型能够获得关于某一主题更全面的信息，但要求它自己提取相关部分。作为我们的搜索引擎，我们使用索引了来自 KILT（Petroni et al., 2021）的维基百科转储的 BM25 检索器（Robertson et al., 1995; Baeza-Yates et al., 1999）。

机器翻译系统

日历

我们的最后一种工具是日历 API，被查询时返回当前日期而不接受任何输入。这为需要一定时间觉察的预测提供时间上下文。

实验

我们研究我们的方法是否使模型能在无进一步监督的情况下使用工具，并自行决定何时以及如何调用哪种可用工具。为测试这一点，我们选择多种下游任务，其中我们假定所考虑工具中至少有一种有用，并在零样本设定下评估性能（第 4.2 节）。

除此之外，我们也确保我们的方法不损害模型的核心语言建模能力；我们通过查看两个语言建模数据集上的困惑度来验证这一点（第 4.3 节）。最后，我们研究学会使用工具的能力如何受模型规模影响（第 4.4 节）。

Limitations While our approach enables LMs to learn how to use a variety of tools in a self-supervised way, there are some clear limitations to what can be achieved with our method in its current form. One such limitation is the inability of Toolformer to use tools in a chain (i.e., using the output of one tool as an input for another tool). This is due to the fact that API calls for each tool are generated independently; as a consequence, there are no examples of chained tool use in the ﬁnetuning dataset. Our current approach also does not allow the LM to use a tool in an interactive way – especially for tools such as search engines, that could potentially return hundreds of different results, enabling a LM to browse through these results or to reﬁne its search query in a similar spirit to Nakano et al. (2021) can be crucial for certain applications. Beyond this, we found models trained with Toolformer to often be sensitive to the exact wording of their input when deciding whether or not to call an API; this is perhaps unsurprising given that LMs are known to be very sensitive to the prompt they are provided with in both zeroand few-shot settings (Jiang et al., 2020; Schick and Schütze, 2021a). Depending on the tool, our method is also very sample-inefﬁcient; for example, processing more than a million documents results in only a few thousand examples of useful calls to the calculator API. A potential solution to this problem might be to iteratively apply our approach, similar to how this is done in related bootstrapping approaches (Schick and Schütze, 2021a; Izacard and Grave, 2021; Parisi et al., 2022). Finally, when deciding whether or not to make an API call, Toolformer currently does not take into account the tool-dependent, computational cost incurred from making an API call. Conclusion We have introduced Toolformer, a language model that learns in a self-supervised way how to use different tools such as search engines, calculators, and translation systems via simple API calls. This is done by ﬁnetuning on a large number of sampled API calls that are ﬁltered based on whether they reduce perplexity on future tokens. Toolformer considerably improves zero-shot performance of a 6.7B parameter GPT-J model, enabling it to even outperform a much larger GPT-3 model on a range of different downstream tasks.

A API Details When sampling and ﬁltering API calls, by default we use values of τs = 0.05 and τf = 1.0 – i.e., we only make API calls at positions where the probability of the <API> token is at least 5%, and we keep API calls if they reduce the loss by at least

1.0. We only keep the top k = 5 such positions and

sample up to m = 5 API calls for each position identiﬁed in a piece of text. Due to the heuristic ﬁltering described below, we generate API calls for the calculator and machine translation system on only a small subset of C; to compensate for this, we set τs = 0.0, k = 20 and m = 10 for these tools. As the resulting sets of API calls are still comparably small, we additionally set τf = 0.5. A.1 Implementation Question Answering We use the Atlas model of Izacard et al. (2022) ﬁnetuned on Natural Questions (Kwiatkowski et al., 2019) as our question answering system. For creating C∗we use Atlaslarge, enabling us to efﬁciently process millions of API calls; during inference, we use the larger Atlas-xxl model. Calculator Our calculator is based on a simple Python script and only supports the operators “+”, “−”, “∗”, and “/”. It does not return any result for syntactically invalid equations. For sampling API calls, we apply heuristic ﬁlters to our subset of CCNet and only process documents that either (i) contain at least three numbers within a window of 100 tokens, where one of these numbers is the result of applying a mathematical operation to the other two, (ii) contain one of the sequences “=”, “equals”, “equal to”, “total of”, “average of” followed by a number, or (iii) contain at least three numbers; for texts that only match the last criterion, we only keep a random subset of 1%. Calendar For creating our dataset C∗, we operate under the assumption that the calendar date in such cases should be the date that the document was created. We approximate this by extracting the date from the URL, if it is present. We ﬁlter out texts for which a date cannot be extracted, leaving around 18% of the documents. Machine Translation For both training and inference, we use the 600M parameter NLLB (Costajussà et al., 2022) as our machine translation (MT) model. The source language is automatically detected using the fastText classiﬁer (Joulin et al., 2016), while the target language is always set to English. Since most of the CCNet dataset is in English, we ﬁlter out the parts that contain only English text before generating API calls. More speciﬁcally, we only keep those paragraphs which contain text chunks in a language other than English preceded and followed by English text. We use text chunks of size 10 tokens. To determine whether the middle text chunk is in a language different than English we again use the fastText classiﬁer with a conﬁdence greater than 0.8. We also ﬁlter out any text chunks that contain only numbers or special symbols. This ﬁltering mechanism allows us to generate data more efﬁciently by focusing our API call generations in places where the MT tool is likely to be helpful. After generating the MT API calls, we additionally remove from our training set those where the input to the MT tool appears after the API call but not before it. While during data generation the model can look ahead to generate API calls, this is not possible at inference time, so we want to dissuade the model from calling the API in such cases. 我们使用 Izacard et al.（2022）在 Natural Questions（Kwiatkowski et al., 2019）上微调的 Atlas 模型作为问答系统。为创建 C* 我们使用 Atlas-large，使我们能高效处理数百万次 API 调用；推理时，我们使用更大的 Atlas-xxl 模型。

计算器

我们的计算器基于简单的 Python 脚本，只支持运算符 “+”、“−”、“∗” 与 “/”。对句法无效的等式它不返回任何结果。为采样 API 调用，我们对 CCNet 子集应用启发式过滤器，只处理（i）在 100 个标记窗口内包含至少三个数字、且其中一个数字是对另外两个应用数学运算的结果的文档，（ii）包含序列 “=”、“equals”、“equal to”、“total of”、“average of” 后跟一个数字的文档，或（iii）包含至少三个数字的文档；对只匹配最后一条标准的文本，我们只保留 1% 的随机子集。

日历

为创建我们的数据集 C*，我们在此类情形下假设日历日期应为文档被创建的日期。我们通过从 URL 提取日期来近似这一点（若其存在）。我们过滤掉无法提取日期的文本，留下大约 18% 的文档。

机器翻译

对训练与推理，我们使用 6 亿参数的 NLLB（Costa-jussà et al., 2022）作为机器翻译（MT）模型。源语言用 fastText 分类器（Joulin et al., 2016）自动检测，目标语言始终设为英语。由于 CCNet 数据集大部分是英语，我们在生成 API 调用前过滤掉只包含英语文本的部分。更具体地，我们只保留那些包含非英语文本块、且其前后为英语文本的段落。我们使用大小为 10 个标记的文本块。为确定中间文本块是否为与英语不同的语言，我们再次使用置信度大于 0.8 的 fastText 分类器。我们也过滤掉只包含数字或特殊符号的任何文本块。这一过滤机制使我们能通过把 API 调用生成聚焦在 MT 工具很可能有帮助的位置，更高效地生成数据。生成 MT API 调用之后，我们额外从训练集中移除那些 MT 工具的输入出现在 API 调用之后而非之前的调用。尽管在数据生成期间模型可以向前看以生成 API 调用，这在推理时不可能，因此我们希望劝阻模型在此类情形中调用 API。

以下是读者评论，用来对照正文，不是作者摘要。开读前只需看导读里的浓缩段；此处供读完方法、表 3–4 与局限段之后展开。

它解决的是「工具调用靠人标」，不是「工具可组合」

Toolformer 把工具使用收成语言建模：采样、执行、按 Δloss 过滤、再微调。对后来的 agent harness，这是关键一刀——模型可以自学何时插入 [Calculator(...)]，而不必每道题写示范。

Cordiverse 要的是运行时：卸掉时把副作用干净收回，以及依赖能声明、能随变化自动协调。这篇没有这两刀。作者自己写得更窄：调用独立采样，所以不能链式；搜索不能改写查询、不能翻多页；也不计算调用成本。工具是插进文本的一次性 API，不是带生命周期的组件。学会调用，不等于拓扑可推理，更不等于可逆卸载。

成绩旁边要一起读的

  • 每题最多一次调用：TEMPLAMA 上「先看日期再问 QA」被纪律禁止，也因训练里从未同时出现。
  • 解码 k=10：调用率被人为抬高；贪心时 WebQS 几乎不怎么调。
  • 规模门槛：小于约 7.75 亿参数，工具几乎帮不上忙——又一次「弱模型过不了工具使用这道门」。

一句话判断

价值在于证明工具使用可以自监督地从语言建模里长出来，6.7B 模型在若干零样本任务上压过更大的不会调工具的模型。缺口是：一次调用、不能交互、没有卸载与依赖语义；过滤标准是下一词，不是任务成功或副作用可回收。Cordiverse 要问的组合问题，这篇刚把插头造出来。
