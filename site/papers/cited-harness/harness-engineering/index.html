全文导读

这是 OpenAI 的工程博文，不是评测论文。数字好看（零行人手写、约百万行、约 1,500 个 PR），但主张容易被收成「Codex 已经能代替工程师」。下面先给出主张、机制、证据与精读路径。读完这一页，再带着一个具体问题进入正文。

一句话主张。 智能体优先之后，稀缺的是人的注意力；工程师的主业变成设计智能体运行框架 / harness——环境、意图规格与反馈环——让 Codex 能可靠地写、评、修、合。

和 AI 工程、智能体、Cordiverse 的关系

Cordiverse 把本文标成引用 [8]：它是工业界对 harness 工程的现场报告。这里的 harness 不是又一套工具调用协议，而是整座仓库如何对 Codex 可读、可强制、可回收：短 AGENTS.md 当地图，docs/ 当记录源，定制 linter 焊死分层，后台任务像垃圾回收一样清「AI slop」。

对 AI 工程的用处可以收成一句：把「催模型再试一次」改成「缺什么能力，就把它做成智能体读得懂、机器强制得了的东西」。它和 Anthropic 的长时 harness（[9]）同一条谱系——都承认模型会漂、会自我表扬、会复制仓里的坏模式——但切口不同：本文几乎不谈多智能体对抗式评审之外的生成–评估拆分，而把力气花在仓库作为系统的记录源。

它没有处理组件卸载时如何收回副作用，也没有声明工具之间的依赖该如何随拓扑变化自动协调。那是 Cordiverse 要补的时空可组合性。展开判断见独立的读后评论，此处不占导读。

问题从哪来

团队给自己加上约束：零行人工手写代码，数周内交付约百万行。早期慢，不是 Codex 不会写，而是环境欠规范：没有对智能体可读的 UI、日志、架构边界和知识地图。人的时间成了唯一固定约束。

缺的不是更长的系统提示，而是一套能让智能体深度优先拆任务、自审互评、按 worktree 启动应用、用指标验收，并在高吞吐下便宜纠错的控制系统。

机制（地图 · 可读性 · 不变量 · 回收）

  • 人提示、智能体执行：PR 由 Codex 打开；Ralph Wiggum Loop 让它本地自审、请求额外智能体评审，循环到评审者满意。
  • 仓库当记录源：放弃「一份巨大的 AGENTS.md」；约 100 行目录指向结构化 docs/。Google Docs 与 Slack 对智能体等于不存在。
  • 应用与可观测性可读：按 git worktree 启动实例；Chrome DevTools Protocol + skills 看 DOM / 截图；隔离的 LogQL / PromQL 让 SLO 提示可执行。
  • 强制架构与品味：每域固定层（Types → … → UI），横切只经 Providers；定制 lint 把修复说明注入上下文。约束是速度的前置条件，不是事后补丁。
  • 高吞吐合并 + 垃圾回收：最少阻塞门、短 PR、片状失败后续补；「黄金原则」后台扫描偏差并开小重构 PR，避免每周五人工清 slop。

作者实际贡献了什么

  • 现场约束：内部 beta、外部 alpha、数百内部用户；约百万行、约 1,500 个 PR；三人阶段人均每天 3.5 个 PR。
  • 角色重定义：人排优先级、译验收、看结果；卡住就补工具 / 护栏 / 文档，并仍由 Codex 写修复。
  • 端到端门槛：单提示可核验现状、复现并录像、修复、再核验、开 PR、修构建、必要时升级、再合并——作者明确说不可无类似投入就外推。
  • 仍开放：完全由智能体生成的系统，架构连贯性如何跨年演化；人的判断如何编码成复利。

第 2 / 24 页

We intentionally chose this constraint so we would build what was necessary to increase engineering velocity by orders of magnitude. We had weeks to ship what ended up being a million lines of code. To do that, we needed to understand what changes when a software engineering team’s primary job is no longer to write code, but to design environments, specify intent, and build feedback loops that allow Codex agents to do reliable work. This post is about what we learned by building a brand new product with a team of agents— what broke, what compounded, and how to maximize our one truly scarce resource: human time and attention. We started with an empty git repository The first commit to an empty repository landed in late August 2025. The initial scaffold—repository structure, CI configuration, formatting rules, package manager setup, and application framework— was generated by Codex CLI using GPT‑5, guided by a small set of existing templates. Even the initial AGENTS.md file that directs agents how to work in the repository was itself written by Codex.

我们有意选择这一约束，以便构建那些能把工程速度再提高几个数量级所必需的东西。我们只有数周时间，却要交付最终约百万行代码的产物。要做到这一点，就必须弄清：当软件工程团队的主业不再是写代码，而是设计环境、明确意图、并搭建能让 Codex 智能体可靠工作的反馈环时，什么会改变。

本文讲述我们用一队智能体从零做出新产品时学到的东西——什么坏了、什么会复利，以及如何最大化我们真正稀缺的资源：人的时间与注意力。

There was no pre-existing human-written code to anchor the system. From the beginning, the repository was shaped by the agent. Five months later, the repository contains on the order of a million lines of code across application logic, infrastructure, tooling, documentation, and internal developer utilities. Over that period, roughly 1,500 pull requests have been opened and merged with a small team of just three engineers driving Codex. This translates to an average throughput of 3.5 PRs per engineer per day, and surprisingly the throughput has increased as the team has grown to now seven engineers. Importantly, this wasn’t output for output’s sake: the product has been used by hundreds of users internally, including daily internal power users. Throughout the development process, humans never directly contributed any code. This became a core philosophy for the team: no manually-written code. Redefining the role of the engineer The lack of hands-on human coding introduced a different kind of engineering work, focused on systems, scaffolding, and leverage.

Early progress was slower than we expected, not because Codex was incapable, but because the environment was underspecified. The agent lacked the tools, abstractions, and internal structure required to make progress toward high-level goals. The primary job of our engineering team became enabling the agents to do useful work. In practice, this meant working depth-first: breaking down larger goals into smaller building blocks (design, code, review, test, etc), prompting the agent to construct those blocks, and using them to unlock more complex tasks. When something failed, the fix was almost never “try harder.” Because the only way to make progress was to get Codex to do the work, human engineers always stepped into the task and asked: “what capability is missing, and how do we make it both legible and enforceable for the agent?” Humans interact with the system almost entirely through prompts: an engineer describes a task, runs the agent, and allows it to open a pull request. To drive a PR to completion, we instruct Codex to review its own changes locally, request additional specific agent reviews both locally and in the cloud, respond to any human or agent given feedback, and iterate in a loop until all agent reviewers are satisfied (effectively this is a ). We regularly see single Codex runs work on a single task for upwards of six hours (often while the humans are sleeping). We made repository knowledge the system of record Context management is one of the biggest challenges in making agents effective at large and complex tasks. One of the earliest lessons we learned was simple: give Codex a map, not a 1,000-page instruction manual. We tried the “one big ” approach. It failed in predictable ways: Context is a scarce resource. A giant instruction file crowds out the task, the code, and the relevant docs—so the agent either misses key constraints or starts optimizing for the wrong ones. Too much guidance becomes nonguidance. When everything is “important,” nothing is. Agents end up pattern-matching locally instead of navigating intentionally. It rots instantly. A monolithic manual turns into a graveyard of stale rules. AGENTS.md

我们把仓库知识做成系统的记录源

上下文管理是让智能体在大型复杂任务上有效的最大挑战之一。我们最早学到的教训很简单：给 Codex 一张地图，而不是一千页说明书。

我们试过「一份巨大的 AGENTS.md」做法。它以可预见的方式失败了：

上下文是稀缺资源。巨型指令文件挤掉任务、代码与相关文档——于是智能体要么漏掉关键约束，要么开始为错误的约束做优化。

指导太多就等于没有指导。当一切都「重要」，就没有什么是重要的。智能体最终做局部模式匹配，而不是有意识地导航。

本页列出端到端闭环：复现、录像、修复、再录像、开 PR、修构建、必要时升级、再合并。同时警告：智能体会复制仓里已有的坏模式，熵会累积。 这很重要，因为它说明自主不是终点，还要有垃圾回收。 类比：复印机很勤快，原稿上的污点也会被一张张印出去。

第 21 / 24 页

Initially, humans addressed this manually. Our team used to spend every Friday (20% of the week) cleaning up “AI slop.” Unsurprisingly, that didn’t scale. Instead, we started encoding what we call “golden principles” directly into the repository and built a recurring cleanup process. These principles are opinionated, mechanical rules that keep the codebase legible and consistent for future agent runs. For example: (1) we prefer shared utility packages over handrolled helpers to keep invariants centralized, and (2) we don’t probe data “YOLO-style”— we validate boundaries or rely on typed SDKs so the agent can’t accidentally build on guessed shapes. On a regular cadence, we have a set of background Codex tasks that scan for deviations, update quality grades, and open targeted refactoring pull requests. Most of these can be reviewed in under a minute and automerged. This functions like garbage collection. Technical debt is like a high-interest loan: it’s almost always better to pay it down continuously in small increments than to let it compound and tackle it in painful bursts. Human taste is captured once, then enforced continuously on every line of code. This also lets us catch and resolve bad patterns on a daily basis, rather than letting them spread in the code base for days or weeks.

起初人手工处理。我们团队曾经每周五（一周的 20%）清理「AI slop」。不出所料，这无法扩展。

于是我们开始把所谓「黄金原则」直接编码进仓库，并建立周期性清理流程。这些原则是有立场的机械规则，让代码库对未来的智能体运行保持可读与一致。例如：（1）我们偏好共享工具包而非手搓辅助，以把不变量集中；（2）我们不「YOLO 式」探数据——我们核验边界或依赖带类型的 SDK，以免智能体意外建立在猜出来的形状上。按固定节奏，一组后台 Codex 任务扫描偏差、更新质量评分，并打开针对性的重构拉取请求。其中多数可在一分钟内评审并自动合并。

这像垃圾回收。技术债像高利贷：几乎总是更好连续小额偿还，而不是让它复利后再痛苦地一次性处理。人的品味被捕捉一次，然后在每一行代码上持续强制。这也让我们能按日抓住并化解坏模式，而不是让它们在代码库里扩散数日或数周。

白话解读

本页讲不再每周五人工清「AI slop」，而是把黄金原则写进仓库，后台 Codex 扫偏差、打分、开小重构 PR，多数一分钟内合。技术债要像垃圾回收一样连着还。 这很重要，因为它把品味从周末大扫除变成日更的机械执行。 类比：与其月底通宵洗碗，不如每用完一只碗就放进洗碗机。

第 22 / 24 页

What we’re still learning This strategy has so far worked well up through internal launch and adoption at OpenAI. Building a real product for real users helped anchor our investments in reality and guide us towards long-term maintainability. What we don’t yet know is how architectural coherence evolves over years in a fully agentgenerated system. We’re still learning where human judgment adds the most leverage and how to encode that judgment so it compounds. We also don’t know how this system will evolve as models continue to become more capable over time. What’s become clear: building software still demands discipline, but the discipline shows up more in the scaffolding rather than the code. The tooling, abstractions, and feedback loops that keep the codebase coherent are increasingly important. Our most difficult challenges now center on designing environments, feedback loops, and control systems that help agents accomplish our goal: build and maintain complex, reliable software at scale. 我们还不知道的是：在完全由智能体生成的系统里，架构连贯性如何随年份演化。我们仍在学习人的判断在何处杠杆最大，以及如何编码这种判断使之复利。我们也不知道，随着模型持续变强，这一系统将如何演化。

读后评论 · 非论文原文

仓库对智能体可读了，卸载与依赖还没有语义

以下是读者评论，用来对照正文，不是作者摘要。开读前只需看导读里的浓缩段；此处供读完知识库布局、分层规则与黄金原则之后展开。

它把 harness 写成控制系统，而不是提示词技巧

这篇最有用的地方，是把「智能体优先」从模型能力叙事拽回工程：人不再以手写补丁为产出，而以环境、意图与反馈环为产出。AGENTS.md 缩成目录、docs/ 当记录源、CDP / LogQL 让验收可执行、分层用 linter 焊死——这些都是在增加 Codex 的可读性与可强制性。对正在长出来的 agent harness，这比再写一段更长的系统提示更接近真实现场。

高吞吐合并哲学也值得单独记下：纠正便宜、等待昂贵。它只在「后续修复同样由智能体便宜完成」时成立；一旦修复仍要人盯，最少阻塞门会把熵直接送进主干。

和 Cordiverse 的接口，也是缺口

Cordiverse 引用 [8]，看重的是工业界已经承认：软件生命周期越来越大的部分由智能体承担，脚手架本身必须成为一等设计对象。前驱在于——工具、文档、评审、回收都被写进仓库，由 Codex 自己改 harness。

窄在于——生命周期几乎停在「写进去、强制住、用后台任务清掉坏模式」。黄金原则可以开重构 PR，文档园艺可以修过期链接，但没有「这条能力过期了、与另一条冲突了、权限与副作用该一并撤掉」的语义。worktree 级隔离拆掉的是一次任务的日志栈，不是组件从运行时卸载时的可逆效应。Providers 是分层门禁，不是反应式余效应：依赖变了，谁该停、谁该等，仍靠人把规则再编码进 lint。

那正是 Cordiverse 用可逆效应与反应式余效应要管的事：造得出、强制得住，还要卸得干净、依赖跟得上。

作者已点名、但仍开放

  • 不可外推（第 20 页）：端到端闭环绑死在这座仓库的结构与工具上。没有类似投入，不应假定换一个仓也能「单提示合入」。
  • 跨年连贯性（第 22 页）：完全由智能体生成的系统，架构如何在年份尺度上演化，作者明确说还不知道。
  • 判断如何复利：人的品味被回写成文档或 lint，但「何处必须由人判断」仍是开放的控制问题，不是已证明的元理论。

读 harness 时额外要盯的

  • 「无聊技术」与自研小工具（如 map-with-concurrency）提高了仓内可推理性，也增加了私有表面积：卸载或替换时，没有依赖声明可自动通知调用方。
  • 智能体对智能体评审把人从必经之路拿掉，同时把失败模式变成「评审者共享同一套仓内偏见」。垃圾回收能扫风格偏差，扫不掉集体跑偏的产品判断。
  • 第 8、13、24 页信息量低；不要把页脚导航读成正文论据。

一句话判断

价值在于把 harness 工程写成可观察的现场：地图式知识、强制不变量、可读的应用与指标、高吞吐下的回收。对未来智能体仍缺的是：这些规则与工具进入长跑运行时之后，如何安全升级、如何卸载与回收副作用、如何表达依赖。本文把仓库变成了 Codex 读得懂的世界；Cordiverse 要问的是，这个世界里的组件如何组合与拆卸。

若只带着一个问题回正文：盯 第 10 页的记录源，和 第 21 页黄金原则——强制得住之后，卸得掉吗？
