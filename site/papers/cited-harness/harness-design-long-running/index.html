这是 Anthropic 的工程博文，容易被收成「再堆两个智能体就更强」。下面先给出主张、机制、证据与精读路径。读完这一页，再带着一个具体问题进入正文。

一句话主张。 长时自主编码的上限往往不在模型，而在智能体运行框架 / harness：把主观品味写成可打分标准，把干活与打分拆开，再随模型变强把不再承重的脚手架拆掉。

和 AI 工程、智能体、Cordiverse 的关系

Cordiverse 把本文标成引用 [9]：它是长时应用开发里 harness 如何随模型能力移动的现场。和 OpenAI 的 harness 工程（[8]）同一条谱系——都承认智能体会漂、会自我表扬、会交看起来完整其实是桩的活——但切口不同：本文用 GAN 式的规划器 / 生成器 / 评估器，并用 Playwright 真点页面，而不是把力气主要花在仓库记录源与分层 lint。

对 AI 工程的用处可以收成一句：每个 harness 组件都编码了「模型自己做不到什么」；模型一升级，这些假设要压测、要做减法。《如何构建有效的智能体》里「尽可能简单，只在需要时加复杂度」，在这里被写成可观察的迭代：Sonnet 4.5 要上下文重置，Opus 4.5 可改压缩，Opus 4.6 可去掉冲刺。

它没有处理评估器、规划器、契约文件在运行时如何卸载，也没有依赖随拓扑变化自动协调的语义。那是 Cordiverse 要补的时空可组合性。展开判断见读后评论。

问题从哪来

旧 harness（初始化智能体 + 一次一个功能 + 交接产物）和社区里的 Ralph Wiggum 循环都能抬基线，但复杂任务仍脱轨。作者观察到两类病：上下文填满后失连贯，以及「上下文焦虑」提前收工；另一类是自我评估偏正向——设计题没有二元测试，软件题也能看起来惊人、核心循环是坏的。

缺的不是更长的单智能体提示，而是可打分的标准、独立的怀疑评估器，以及随模型边界外移而可拆的编排。

机制（标准 · 三角色 · 契约 · 减法）

  • 四条前端标准：设计质量、原创性、工艺、功能性；前两项加权，惩罚紫渐变白卡片之类 slop。评估器用 Playwright MCP 导航实况页，5–15 轮，可跑四小时。
  • 压缩 vs 重置：压缩不断档但治不好焦虑；重置要交接产物带够状态。Opus 4.5 之后本 harness 丢掉重置，改连续会话 + 自动压缩。
  • 三智能体：规划器把 1–4 句扩成有野心的规格（不写死实现）；生成器按冲刺实现（React / Vite / FastAPI）；评估器按硬阈值打回。冲刺前协商「完成」契约，用文件通信。
  • 随模型做减法：Opus 4.6 去掉冲刺，评估器改为结束时单次通过，且只在任务超出模型独做边界时才值成本。

To break through, I sought out novel AI engineering approaches that held across two quite different domains, one defined by subjective taste, the other by verifiable correctness and usability. Taking inspiration from Generative Adversarial Networks (GANs), I designed a multi-agent structure with a generator and evaluator agent. Building an evaluator that graded outputs reliably—and with taste—meant first developing a set of criteria that could turn subjective judgments like “is this design good?” into concrete, gradable terms. I then applied these techniques to long-running autonomous coding, carrying over two lessons from our earlier harness work: decomposing the build into tractable chunks, and using structured artifacts to hand off context between sessions. The final result was a three-agent architecture—planner, generator, and evaluator—that produced rich full-stack applications over multi-hour autonomous coding sessions. Why naive implementations fall short We've previously shown that harness design has a substantial impact on the effectiveness of long running agentic coding. In an earlier experiment, we used an initializer agent to decompose a product spec into a task list, and a coding agent that implemented the tasks one feature at a time before handing off artifacts to carry context across sessions. The broader developer community has converged on similar insights, with approaches like the "Ralph Wiggum" method using hooks or scripts to keep agents in continuous iteration cycles. But some problems remained persistent. For more complex tasks, the agent still tends to go off the rails over time. While decomposing this issue, we observed two common failure modes with agents executing these sorts of tasks. First is that models tend to lose coherence on lengthy tasks as the context window fills (see our post on context engineering). Some models also exhibit "context anxiety," in which they begin wrapping up work prematurely as they approach what they believe is their context limit. Context resets—clearing the context window entirely and starting a fresh agent, combined with a structured handoff that carries the previous agent's state and the next steps—addresses both these issues.

为何朴素实现不够用

When asked to evaluate work they've produced, agents tend to respond by confidently praising the work—even when, to a human observer, the quality is obviously mediocre. Whether a layout feels polished or generic is a judgment call, and agents reliably skew positive when grading their own work. Separating the agent doing the work from the agent judging it proves to be a strong lever to address this issue. The separation doesn't immediately eliminate that leniency on its own; the evaluator is still an LLM that is inclined to be generous towards LLM-generated outputs. But tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work, and once that external feedback exists, the generator has something concrete to iterate against. Iterating on the harness The first set of harness results was encouraging, but it was also bulky, slow, and expensive. The logical next step was to find ways to simplify the harness without degrading its performance. This was partly common sense and partly a function of a more general principle: every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing, both because they may be incorrect, and because they can quickly go stale as models improve. Our blog post Building Effective Agents frames the underlying idea as "find the simplest solution possible, and only increase complexity when needed," and it's a pattern that shows up consistently for anyone maintaining an agent harness. In my first attempt to simplify, I cut the harness back radically and tried a few creative new ideas, but I wasn't able to replicate the performance of the original. It also became difficult to tell which pieces of the harness design were actually load-bearing, and in what ways. Based on that experience, I moved to a more methodical approach, removing one component at a time and reviewing what impact it had on the final result. As I was going through these iteration cycles, we also released Opus 4.6, which provided further motivation to reduce harness complexity. There was good reason to expect 4.6 would need less scaffolding than 4.5 did. From our launch blog: "[Opus 4.6] plans more carefully, sustains agentic tasks for longer, can operate more reliably in larger codebases, and has better code review and debugging skills to catch its own mistakes." It also improved substantially on long-context retrieval. These were all capabilities the harness had been built to supplement. Removing the sprint construct I started by removing the sprint construct entirely. The sprint structure had helped to decompose work into chunks for the model to work coherently. Given the improvements in Opus 4.6, there was good reason to believe that the model could natively handle the job without this sort of decomposition. I kept both the planner and evaluator, as each continued to add obvious value. Without the planner, the generator under-scoped: given the raw prompt, it would start building without first speccing its work, and end up creating a less feature-rich application than the planner did.

迭代该 harness

第一组 harness 结果令人鼓舞，但也笨重、缓慢、昂贵。合乎逻辑的下一步是：在不降低表现的前提下简化 harness。这既是常识，也来自更一般的原则：harness 里每个组件都编码了「模型自己做不到什么」的假设，这些假设值得压测——既因为它们可能错，也因为模型一改进它们会很快过时。我们的博文《如何构建有效的智能体》把底层想法写成「找到尽可能简单的解，只在需要时增加复杂度」，对任何维护智能体运行框架的人，这都是反复出现的模式。

我第一次简化时把 harness 砍得太狠，并试了些新点子，却复制不出原版表现。也很难分辨哪些设计是真正承重的、以何种方式承重。基于那次经验，我改用更有方法的做法：一次拿掉一个组件，再看对最终结果的影响。

走过这些迭代时，我们也发布了 Opus 4.6，这进一步推动降低 harness 复杂度。有充分理由预期 4.6 需要的脚手架少于 4.5。发布博文写道：「[Opus 4.6] 规划更仔细，能把智能体任务维持得更久，能在更大代码库里更可靠地运作，并有更好的代码评审与调试技能来抓住自己的错误。」它在长上下文检索上也显著改进。这些正是 harness 一直在补的能力。

去掉冲刺构造

我首先完全去掉冲刺构造。冲刺结构曾帮助把工作分解成模型能连贯处理的块。鉴于 Opus 4.6 的改进，有充分理由相信模型可以本地处理这份工作，而不需要这种分解。

我保留规划器与评估器，因为二者仍明显增值。没有规划器，生成器会欠范围：拿到原始提示，它会不先做规格就开始建，最终做出的应用功能不如规划器那版丰富。

With the sprint construct removed, I moved the evaluator to a single pass at the end of the run rather than grading per sprint. Since the model was much more capable, it changed how load-bearing the evaluator was for certain runs, with its usefulness depending on where the task sat relative to what the model could do reliably on its own. On 4.5, that boundary was close: our builds were at the edge of what the generator could do well solo, and the evaluator caught meaningful issues across the build. On 4.6, the model's raw capability increased, so the boundary moved outward. Tasks that used to need the evaluator's check to be implemented coherently were now often within what the generator handled well on its own, and for tasks within that boundary, the evaluator became unnecessary overhead. But for the parts of the build that were still at the edge of the generator’s capabilities, the evaluator continued to give real lift. The practical implication is that the evaluator is not a fixed yes-or-no decision. It is worth the cost when the task sits beyond what the current model does reliably solo. Alongside the structural simplification, I also added prompting to improve how the harness built AI features into each app, specifically getting the generator to build a proper agent that could drive the app's own functionality through tools. That took real iteration, since the relevant knowledge is recent enough that Claude's training data covers it thinly. But with enough tuning, the generator was building agents correctly. 读后评论 · 非论文原文

评估器拆得出、脚手架拆得动，卸载仍没有语义

以下是读者评论，用来对照正文，不是作者摘要。开读前只需看导读里的浓缩段；此处供读完三角色、游戏对照与 V2 做减法之后展开。

它解决的是「自己给自己打高分」和「看起来完整」

这篇最锋利的观察不是「多智能体更好」，而是：生成器与评估器若是同一个上下文里的同一角色，宽松是默认值。分开之后，评估器仍是 LLM，仍会自我开脱，但把怀疑调进独立提示比让生成器自黑可操作。Playwright 真点页面，把「静图好看」从验收里拿掉，solo 那条断掉的游戏运行时接线才暴露出来。

V2 更进一步：评估器不是固定工位。任务落在模型独做边界之内，它是开销；落在边界之外，它接的是「展示型核心功能」——时间线不能拖、录音是桩。这对 harness 工程比又一张成本表更有用：组件的存在理由是假设，假设过期就要拆。

和 Cordiverse 的接口，也是缺口

Cordiverse 引用 [9]，看重长时构建里上下文交接、角色分工与随模型做减法。前驱在于——harness 被明确写成可增可减的编排，而不是焊死的工作流。

窄在于——减法发生在作者改提示、拿掉冲刺、把评估器挪到末尾这一层，不是运行时卸载。规划器写出的规格、冲刺契约文件、评估器打开的浏览器会话，任务结束后如何收回副作用、下一场构建如何声明「还依赖这条 skill / 这条 MCP」，文中没有语义。文件通信是握手，不是余效应：契约改了，谁该停、谁该重谈，靠人再写一轮编排。

Claude 听不见，所以 DAW 的品味 QA 先天弱——这提醒：评估器的感官就是 harness 的边界。Cordiverse 要补的，是这些边界变化时如何可逆、如何通知依赖方，而不只是作者下次实验时记得拆组件。

作者已点名、但仍开放

  • 中间轮可能更好（第 5 页）：分数上升不等于最后一轮最值得留下。harness 没有「冻结中间产物」的版本语义，只有继续迭代。
  • QA 能力上限（第 12 页）：深层嵌套功能仍漏；评估器本身要多轮调提示才像样。
  • 产品直觉（第 10 页）：先做精灵再铺关，harness 没补上。作者把它留给「针对性迭代」，不是已解决问题。

读 harness 时额外要盯的

  • 200 美元 vs 9 美元不是公平的同等时间对照；质量差成立，成本外推要自己加权。
  • 「博物馆品质」之类用语会塑造视觉收敛——标准文本本身就是生成器的隐式奖励，写歪了会整族跑偏。
  • 第 19–23 页基本是页脚；不要把导航读成附录证据。

一句话判断

价值在于把主观质量做成共享评分表，把干活与打分拆开，并用模型升级证明 harness 该做减法。缺口是：拆组件仍是作者侧的编辑，不是运行时的可逆卸载与依赖通知。组合发生了，回收与协调还没有。Cordiverse 要问的，正是下一组「有趣组合」如何在卸掉时不留尾巴。

若只带着一个问题回正文：盯 第 7 页契约，和 第 14 页「评估器不是固定是否」——上场容易，退场有没有协议？
